## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | **Apple Music CLI** (제출용 프로젝트명 확정 필요) |
| 한 줄 정의 | **의도를 받아 곡을 고르고, 왜 골랐는지 말하고, 반응을 기억하는 미디어 도구 계층.**<br>사람은 터미널로, 에이전트는 API로 **같은 것**을 쓴다 |
| 타겟 사용자 | **에이전트를 일상적으로 쓰는 개발자** — 터미널에 코딩 에이전트를 띄워두고 일하는 사람 |
| 형태 | 도구 서버 + 그 첫 번째 클라이언트인 macOS TUI |
| 없애려는 것 | **"무엇을 틀지는 네가 정해라"** |

> **프로젝트명 주의.** `Apple Music`은 Apple의 상표이므로 제출 파일명·표지에는
> 고유 프로젝트명을 두고 `Apple Music CLI`는 부제로 쓰는 편이 안전하다.

## 2. 문제 정의

### 현황 — 미디어 도구는 리모컨까지만 왔다

에이전트가 음악을 트는 것은 **이미 된다.** Apple Music을 제어하는 MCP 서버가
여럿 공개돼 있고, 그중에는 **도구가 74개**인 것도 있다 (AirPlay 멀티룸 볼륨까지).

그런데 그것들이 노출하는 도구를 보면 전부 같은 성격이다.

```
play(track)   pause()   next()   search(query)
setVolume(n)  createPlaylist(name)   addToPlaylist(id, track)
```

**AppleScript 표면을 그대로 도구로 옮긴 것이다.** 74개여도 마찬가지다.
개수의 문제가 아니라 **층위의 문제**다.

Home Assistant 쪽은 더 노골적이다. 미디어 인텐트가 극히 제한적이고
**음성으로 재생을 시작하는 것 자체가 미지원**이며, 셔플·큐 조작 등은
아예 *"범위 밖"* 으로 명시돼 있다. 미디어 제어는 어디서나 얕게만 다뤄진다.

### 원인 ① — 도구가 명령을 받지 의도를 못 받는다

`play(track)` 을 부르려면 **무엇을 틀지 호출자가 이미 알고 있어야 한다.**

| 도구가 받는 것 | 사람이 실제로 갖고 있는 것 |
|---|---|
| `play("Perth")` | "집중할 수 있는 걸로" |
| `search("Bon Iver")` | "지금 이 시간에 어울리는 거" |
| `createPlaylist("focus")` | "요즘 안 듣던 것 좀 섞어줘" |

그래서 곡 선택은 결국 사람이 하거나, 에이전트가 카탈로그에서 아무거나 집는다.
**고르는 일 자체는 아직 도구화되지 않았다.**

### 원인 ② — 결과가 남지 않는다

무엇을 왜 틀었는지, 사용자가 3초 만에 넘겼는지가 **앱 밖으로 나오지 않는다.**

```
에이전트 → play(track) → Music.app
                          └─ 재생됨. 끝.
                             (왜 골랐는지 · 어떻게 반응했는지 아무데도 없음)
```

그래서 **에이전트는 매번 처음부터 시작한다.** 어제 스킵한 곡을 오늘 또 튼다.
호출은 되는데 **누적되지 않는다.**

### 이것은 사람에게도 똑같은 문제다

고르는 비용이 높으면 늘 아는 것만 고른다. 손이든 에이전트든 같다.
작성자 본인 라이브러리 실측값이다 (`docs/05`).

```
157곡 · 총 재생 777회

담은 곡의 재생 수명 (담은 날 → 마지막 재생일)   중앙값 19일
담은 지 하루 만에 끝난 곡                       32곡 (32%)
상위  5곡 = 전체 재생의 48.8%
상위 24곡 = 전체 재생의 80.0%   ← 곡의 15%
0회 56곡 + 1회뿐 42곡 = 98곡 (62.4%)
```

**담는 행위는 10개월간 계속됐는데, 담은 곡의 수명은 3주다.**
맥락은 분명히 있다 — 재생은 오후(38회)와 출근길(24회)에 몰리고 새벽에는 0이다.
그런데 그 맥락을 받아줄 자리가 어떤 도구에도 없다.

### 배경 — 기존 수단이 안 되는 이유

| 수단 | 노출하는 것 | 없는 것 |
|---|---|---|
| **Apple Music MCP 서버들** | play · pause · search · playlist · volume | **의도 입력 · 선정 근거 · 반응 기록** |
| **Home Assistant** | 제한된 미디어 인텐트 | 음성 재생 시작 자체가 미지원. 그 이상은 범위 밖 |
| **Shortcuts** | 사람이 미리 짠 고정 조합 | 새로운 상황에 대응 못 함 |
| **Apple Music API** | 카탈로그 검색 · 추천 | **재생 이력 없음**, 재생 제어 없음 |
| **스마트 플레이리스트** | 필드 기반 자동 갱신 | 장르·연도·별점뿐. "지금 기분"은 어떤 필드에도 없음 |

## 3. 한 줄로

```
미디어 도구는 리모컨까지 왔다.
의도를 받고, 이유를 말하고, 반응을 기억하는 층이 없다.
```

**그 층을 만든다.**

---

## 4. 핵심 가치 3가지

| # | 가치 | 뜻 |
|---|---|---|
| ① | **의도를 받는다** | 곡 이름이 아니라 상황을 받는다. 고르는 일까지가 도구의 몫이다 |
| ② | **이유를 말한다** | 고른 곡마다 근거 한 줄. 근거 없는 선택은 사람도 에이전트도 검증할 수 없다 |
| ③ | **반응을 기억한다** | 스킵은 버려지지 않는다. 호출이 누적되어 다음 선택을 바꾼다 |

**이 셋이 기존 도구들에 없는 전부다.** 개수로 이기는 게 아니라 층위로 이긴다.

## 5. 주요 기능 — 문제와의 연결

**모든 기능은 위 원인 중 하나에 대응한다.**

| # | 기능 | 해결하는 것 |
|---|---|---|
| **F1** | 자연어 의도로 재생 큐를 만든다 | 원인 ① — 고르는 일을 도구가 맡는다 |
| **F2** | 곡마다 선정 근거를 한 줄로 제시한다 | 가치 ② — 검증 가능한 선택 |
| **F3** | 되물어 그 자리에서 재편성한다 | 원인 ① — 한 번에 못 맞춘 것을 대화로 좁힌다 |
| **F4** | 스킵·완청·좋아요를 반응으로 기록한다 | 원인 ② — 결과를 남긴다 |
| **F5** | 반응에서 취향 규칙을 도출하고 사용자가 관리한다 | 원인 ② — 누적을 사람이 볼 수 있게 |
| **F6** | 라이브러리 재생 쏠림을 진단한다 | 현황 — 문제를 사용자 데이터로 증명 |
| **F7** | 오래 안 들은 곡을 훑고 되살리거나 정리한다 | 현황 — 수명 19일에 대한 직접 대응 |
| **F8** | 안 듣던 곡을 실마리로 카탈로그 유사곡을 탐색한다 | 바깥으로 나가되 **안쪽을 출발점으로** |
| **F9** | 마음에 든 큐를 Apple Music 플레이리스트로 저장한다 | 결과를 앱 생태계에 되돌려 놓음 |
| **F10** | 지금 들리는 곡을 인식한다 (ShazamKit) | 라이브러리 바깥의 곡을 안으로 들이는 경로 |
| **F11** | 인식된 곡이 내 라이브러리에 있는지 대조한다 | 현황 — "갖고 있는데 안 듣는 곡"과 마주치게 함 |

## 6. 시스템 구성

**서버는 TUI의 백엔드가 아니라 도구 표면 그 자체다.**
TUI는 그 도구를 쓰는 첫 번째 클라이언트일 뿐이다.

```
   사람                              에이전트
     │                                  │
     ▼                                  ▼
┌──────────┐                    ┌──────────────┐
│ TUI      │                    │ 코딩 에이전트 │
│ (터미널)  │                    │ 캘린더 · Siri │
└────┬─────┘                    └──────┬───────┘
     │            같은 API              │
     └───────────────┬──────────────────┘
                     ▼
        ┌────────────────────────────┐
        │        도구 서버            │
        │  의도 → 선곡 → 근거 → 반응   │
        │  세션 · 취향 규칙 · 이력     │
        └───┬───────────────────┬────┘
            │ AppleScript       │ Apple Music API
            ▼                   ▼
      ┌───────────┐      ┌──────────────┐
      │ Music.app │      │  카탈로그     │
      └───────────┘      └──────────────┘
              ▲
              │ spawn
        ┌─────────────┐
        │ Shazam 헬퍼  │ (Swift, F10)
        └─────────────┘
```

| 경계 | 담당 |
|---|---|
| 도구 서버 | 의도 해석 · 선곡 · 근거 생성 · 반응 누적 · 취향 규칙 · 라이브러리 색인 |
| TUI | 화면 렌더링, 입력, 로컬 Music.app 제어, 재생 상태 폴링 |
| Shazam 헬퍼 | ShazamKit 이 Swift 전용이므로 별도 바이너리. JSON 으로 결과 반환 |

**호출자가 사람인지 에이전트인지는 `queue_item.origin` 에 남는다.**
그래서 "에이전트가 고른 곡은 스킵률이 높은가" 같은 것도 측정된다.

### 데이터 출처

| 필요한 것 | 출처 |
|---|---|
| **재생 횟수 · 마지막 재생일 · 스킵 횟수** | **Music.app (AppleScript)** — 웹 API 는 재생 이력을 주지 않는다 |
| ISRC · 아트워크 · 유사 아티스트 | Apple Music API |
| 곡 인식 결과 (`appleMusicID`, ISRC) | ShazamKit |
| 무드 · 상황 태그 | **없음 → 생성한다.** Apple 은 오디오 특성을 제공하지 않는다 |

## 7. 범위에서 제외하는 것

**의도적 제외이며 `고려사항` 섹션에 근거와 함께 명시한다.**

| 제외 | 이유 |
|---|---|
| **MCP 서버 패키징** | 이번 범위는 **도구로 쓸 수 있게 설계하는 것**까지. OpenAPI → MCP 변환은 기계적이므로 다음 단계 |
| 멀티 클라이언트 (Raycast · 메뉴바 · Siri) | 클라이언트는 macOS TUI 하나 |
| 음성 입력 / 실시간 STT | 입력은 텍스트로 충분 |
| 팀 · 공유 · 소셜 | 1인용 도구 |
| 벡터 DB · 임베딩 파이프라인 | 라이브러리 규모에서는 메타데이터 질의로 충분 |
| 음원 파일 직접 재생 | Music.app 에 위임 (DRM·코덱 회피) |
| 곡 파일 삭제 | "정리"는 **제외 표시**까지. 원본은 건드리지 않는다 |
| ShazamKit 커스텀 카탈로그 | 기본 카탈로그 + `appleMusicID` 대조로 충분 |
| 상시 백그라운드 청취 | 인식은 명시적 요청 시에만 (`/shazam`) |

## 8. 다음 단계로 열리는 것 (PDF 6장 "고려사항")

도구 계층으로 만들어 두면 아래가 **추가 설계 없이** 따라온다.

| # | 확장 |
|---|---|
| 1 | **클라이언트 확장** — Raycast · 메뉴바 · Shortcuts · Claude Desktop 이 같은 API 를 쓴다 |
| 2 | **작업이 음악을 부른다** — 코딩 에이전트가 리팩터링을 시작하며 집중 큐를 요청하고, 캘린더 에이전트가 회의 10분 전에 볼륨을 낮춘다 |
| 3 | **의도의 출처가 데이터가 된다** — 사람이 고른 곡과 에이전트가 고른 곡의 스킵률을 비교할 수 있다 |
| 4 | **역방향 컨텍스트** — 지금 무엇을 듣고 있는지가 다른 에이전트의 입력이 된다 ("집중 음악 재생 중 = 방해 금지") |
| 5 | **미디어 종류 확장** — 팟캐스트·오디오북이 같은 도구 모양(`의도 → 선택 → 근거 → 반응`)을 쓴다. `track` 을 `media_item` 으로 일반화하면 열린다 |
| 6 | **오디오 출력 조정** — 여러 에이전트가 동시에 소리를 내려 할 때 누가 스피커를 쓸지 조정하는 계층이 필요해진다 |
