## 확정 ① 제품 컨셉 — 하이브리드

| | 내용 |
|---|---|
| 한 문장 | **"확인해보고 연락드리겠습니다"를 없애는 것** |
| 성공 지표 | 질문 대비 "확인 후 회신" 비율이 **시간이 갈수록 감소** |
| 화면·발표 언어 | 어시스턴트형 ("어떻게 말해야 하는가") |
| 데이터 모델 | 원안 5테이블 유지 (엔티티 풍부 → ERD/API 배점 유리) |

### 용어 재정의 (원안 → 확정)

| 원안 | 확정 | 의미 |
|---|---|---|
| `verdict` | `response_mode` | `direct`(즉답) / `conditional`(조건부) / `escalate`(담당자 연결) |
| `fallback_script` | `suggested_script` | 실제로 입에 낼 문구 |
| `deferral` | ~~`knowledge_gap`~~ → **`action_item`** | 09-08 개편. 회의 후 할 일의 한 종류로 흡수 |
| `policy_rule` | `response_rule` | "말해도 되는가" → **"어떻게 말해야 하는가"** |

### 3막 루프 (제품의 전부)

```
1막  미팅 중  질문 발생 → 답 없음 → 🟡 할 말 제공 + knowledge_gap 생성
2막  사후    담당팀이 큐에서 공백을 response_rule로 확정
3막  다음 미팅 같은 질문 → 🟢 1.5초 즉답
```

`response_rule.created_from ↔ knowledge_gap.resolved_by` 양방향 FK가
**"쓸수록 좋아진다"의 데이터 증거**. 반드시 유지.

### 모를 때도 할 말을 준다 (1급 기능)

원안에 없던 추가 결정. 매칭 실패 시 "결과 없음"이 아니라
할 말 문구 + 역질문 유도를 제공하고, 동시에 `knowledge_gap`을 생성한다.
→ `knowledge_gap` 생성 시점이 자연스러워지고, 어시스턴트 성격이 살아남.

## 확정 ② 입력 계층 — 사용자는 아무것도 입력하지 않는다

미팅 중 질문을 타이핑하는 것은 비현실적.
상대가 말을 끝내면 **1.5초 안에 패널에 답이 떠 있어야 한다.**

### 캡처 방식 — Granola 방식 (봇 없이 로컬 캡처)

| 환경 | 방법 | 화자 구분 비용 |
|---|---|---|
| **화상** | 마이크 트랙 = 나 / 시스템 오디오 트랙 = 상대 | **0** (채널 분리) |
| **대면** | 단일 마이크 + 내 목소리 등록(enrollment) | 낮음 (나 1명만 식별) |

- 회의 참가자로 봇이 노출되지 않음 (Otter/Fireflies와 차별)
- 상대방 화면에 아무것도 노출하지 않는다는 원칙과도 일치

### 처리 대상

- **상대방 트랙만** 질문 감지 파이프라인을 태운다 (연산·지연 절반)
- **내 트랙도 저장은 한다** — `"그거 되나요?"` 대명사 해소에 직전 문맥 필요

## 확정 ③ 화자 모델 — 나 vs 나 아님, 단 확장 가능한 구조로

MVP는 이진 구분(host / counterpart)만 한다.
단 **participant를 테이블로 분리**해 1:N 확장 시 스키마 변경이 없게 한다.

```
session
  └─ participant     role(host/counterpart), speaker_label, voice_profile_id
       └─ utterance   participant_id FK
```

| | MVP (1:1) | 확장 (1:N) |
|---|---|---|
| participant 행 수 | 2 | N |
| `role` | host 1 / counterpart 1 | host 1 / **counterpart N** |
| `speaker_label` | null | A, B, C… |
| **스키마 변경** | — | **없음** |

- ❌ `utterance.is_me` 같은 불리언/enum → 확장 불가. 쓰지 않는다.
- 질문 감지 조건은 `participant.role != 'host'` → 상대가 N명이어도 코드 동일
- `speaker_label`은 **미리 만들고 MVP에서 null로 비워둔다** (확장성의 문서적 증거)

### 이 설계의 이점

조사 결과 "화자 수가 늘수록 diarization 정확도 하락"이 확인됨.
**나 1명만 식별하면 되므로 이 문제를 구조적으로 회피한다.**

## 확정 ④ 처리 파이프라인

```
① 오디오 2트랙 스트리밍
        ↓
② STT (턴 종료 감지 내장 공급자) → utterance 생성
        ↓  role != host 만
③ 질문 감지   1차: 규칙(?, ~되나요/~인가요/~얼마/~가능한가)
              2차: 소형모델 (규칙 통과분만)
        ↓
④ 질문 정규화  직전 3~5 발화로 대명사 해소
        ↓
⑤ 병렬 검색  ─┬─ knowledge (audience_level 필터)
              └─ response_rule
        ↓
⑥ 판정 + 문구 생성 (headline 먼저 스트리밍)
        ↓
⑦ 패널 표시 / 매칭 실패 시 knowledge_gap 생성
```

**무거운 모델 호출은 ⑥ 한 번뿐.**

### 1.5초 예산 (→ 기획서 "고려사항" 핵심 자료)

| 단계 | 예산 | 근거 |
|---|---|---|
| 턴 종료 감지 | 300ms | STT VAD 내장 (`semantic_vad`) |
| STT 최종 확정 | 150ms | 인터림 선수신. **OpenAI는 공식 지연 수치 미공개 → MVP 첫 작업으로 실측** |
| 질문 감지(규칙) | ~0ms | 정규식 |
| 질문 감지(소형모델) | 200ms | 규칙 통과분만 |
| 검색(병렬) | 200ms | 벡터 2건 동시 |
| 첫 토큰(headline) | 500ms | TTFT |
| **누적** | **~1,150ms** | 여유 350ms |

**모든 아키텍처 선택이 이 표에서 정당화된다.**
검색을 순차로 하면 400ms → 예산 초과 → 그래서 병렬.
질문 감지를 LLM 1회로 하면 +500ms → 그래서 규칙 1차 필터.

## 확정 ⑤ MVP 입력 소스 추상화

```
AudioSource (interface)
  ├─ LiveAudioSource    실제 STT 스트리밍
  └─ ScriptedSource     사전 녹음 / 스크립트 재생
```

둘 다 ② 이후 파이프라인을 **완전히 동일하게** 탄다.
데모는 `ScriptedSource`로 안정적으로, 라이브는 한 번만 시연.
오디오 없이 파이프라인을 재현 가능하게 테스트하려면 어차피 필요한 구조.

## 조사 결과 요약 (근거 자료)

### 실시간 화자분리는 상용 표준
별도 API 아님. 같은 WebSocket으로 transcript + speaker label 수신.
AssemblyAI / Deepgram / Speechmatics / Amazon Transcribe 모두 제공.

### 지연 실측
| 출처 | 수치 |
|---|---|
| AssemblyAI Universal-3.5 Pro Realtime | ~221ms turn delivery |
| Hamming.ai 독립 벤치 (통화 400만건) | P50 307ms |
| AssemblyAI Universal-3 Pro Streaming | P50 ~150ms / P90 ~240ms |
| Deepgram | sub-300ms |
| **Cresta (실시간 코칭 제품)** | **200ms 이내 next-best-action** |

지연의 대부분은 diarization 연산이 아니라 **말이 끝나길 기다리는 시간**.
→ 화자분리를 넣어도 1.5초 예산이 깨지지 않는다.

### 화자 수 한계
`max_speakers` 1~10. 화자가 늘수록 정확도 하락 (사람당 오디오 부족).
2명이 가장 안정. → 우리의 "나 vs 나 아님" 전략이 유효한 이유.

### 스트리밍 diarization의 구조적 한계
- 되돌릴 수 없음 (판정 확정 후 수정 불가)
- 초반 턴 부정확
- 1초 미만 발화는 `UNKNOWN`
- AssemblyAI는 종료 후 ~0.5s 재클러스터링으로 보정

### 대면/단일 마이크
중첩 발화 구간 **DER 25~30%**. 변수는 음질·화자 수·중첩량.
→ 대면 1:N은 가능하나 화상 1:1보다 명확히 어려운 조건.

### 채널 분리 (AssemblyAI 문서 직접 언급)
> 각 화자가 별도 채널이면 **diarization을 아예 건너뛸 수 있다.**

국내 콜센터도 동일 (Furence: 상담사·고객 각각 녹취 / ZiBox: 금융권 실시간 모니터링).

### 제품 선례
| 계층 | 제품 | 특징 |
|---|---|---|
| 사후 분석 | Gong, Chorus | 캘린더 연동 자동 참석, CRM 연동 |
| **실시간 가이던스** | **Balto** | 라이브 스크립트·**배틀카드**·컴플라이언스. 누적 4억 통 |
| **실시간 가이던스** | **Cresta** | 200ms 내 next-best-action + 지식 답변 |
| 노트테이커(봇) | Otter, Fireflies, Fathom | 참가자로 입장 |
| **노트테이커(봇 없음)** | **Granola, Meetily** | 마이크+시스템오디오 로컬 캡처 |

- **Balto의 "배틀카드" = 우리의 `suggested_script`.** 카테고리 검증됨 → 실현 가능성 방어 근거
- Granola, Grain, Zoom, Supernormal, Fireflies가 모두 AssemblyAI 인프라 사용

### Whisper 재평가
엔드포인팅은 Whisper의 일이 아니라 **VAD(Silero 등)의 일**.
"약하다"는 부정확 → **"내장이 아니라 직접 조립해야 한다"**가 정확.
진짜 문제는 지연: whisper-streaming 계열 실측 **1~3초** → 1.5초 예산과 충돌.
(`WhisperPipe` 등 스트리밍화 연구는 활발 → 조립 영역이지 즉시 사용 영역은 아님)

### 한국어 실시간 STT — AssemblyAI·Deepgram Flux 탈락 (2026-09-08 조사)

위 지연 수치는 전부 **영어 벤치**였다. 한국어 스트리밍 지원 여부를 확인한 결과:

| 공급자 | 한국어 실시간 | 턴 종료 감지 | 판단 |
|---|---|---|---|
| AssemblyAI Universal-3.5 Pro Streaming | ❌ 18개 언어에 없음 | ✅ | **탈락** |
| Deepgram Flux | ❌ 10개 언어에 없음 | ✅ | **탈락** |
| Deepgram Nova-3 | ✅ | ❌ VAD 직접 조립 | 탈락 |
| **OpenAI `gpt-live-transcribe`** | ✅ 57개 언어* | ✅ `server_vad` / `semantic_vad` | **채택** |
| ElevenLabs Scribe v2 Realtime | ✅ 90+ 언어 | ✅ 무음 기반 VAD | 2순위 |
| 리턴제로 (VITO) | ✅ 한국어 CER 5.91% (최저) | 확인 필요 | 정확도 병목 시 교체 후보 |

*OpenAI 모델 페이지에 언어 목록 미명시. 발표문 57개 언어 + 전작 `gpt-4o-transcribe` 한국어 지원 근거.
**MVP 착수 전 1분 한국어 테스트로 확정.**

채택 이유: 턴 감지 내장으로 예산 표 300ms 유지 / 트랙당 세션 1개로 화자분리 불필요 /
질문 감지·임베딩·생성과 **단일 벤더**. 리턴제로 교체가 필요해도 `AudioSource` 뒤에 있어 파이프라인 변경 없음.
