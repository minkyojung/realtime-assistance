설계 원칙 4개

①자연어 요청은 비동기다

POST /turns 는 202 를 즉시 돌려주고, 화면은 GET /turns/{turnId} 로 진행을 본다. 선곡은 초 단위다 — 기다리게 하면 그동안 입력창이 죽는다.

②실시간 값은 저장하지 않는다

재생 위치 · 섞기 · 반복은 서버가 Music.app 에 그때그때 물어 돌려준다. GET /playback 의 응답에서 DB 컬럼에서 오는 것은 곡 정보뿐이다.

③관문은 로그인이 아니라 권한이다

그래서 401 이 없다. 대신 403 AUTOMATION_PERMISSION_DENIED 와 503 MUSIC_APP_NOT_RUNNING 이 있다.

④AI 실패는 HTTP 에러가 아니다

요청은 이미 202 로 받았으므로 실패는 turn.errorCode 로 온다. 근거를 못 만들어도 reason 이 null 일 뿐 큐는 그대로 돈다.

비동기 요청 한 건이 도는 길 — POST /turns

POST /turns“한 시간짜리, 발표 전에 차분해지는, 한 번도 안 들어본 곡으로”
→
202 Accepted{ turnId, status: "running" }
입력창은 계속 쓸 수 있다
→
GET /turns/{turnId}화면은 답이 앉을 자리에 스피너를 앉히고 이것을 반복한다
→
status: done큐가 갱신되고, 곡마다 reason 한 줄이 붙는다
→
GET /queue · /messages대화 띠에 답과 근거가 남고, 상태줄에 이번에 쓴 돈이 더해진다
실패도 이 길로 온다. 요청은 이미 202 로 받았으므로 모델이 답하지 않아도 HTTP 는 200 이고, turn.status = failed · errorCode = MODEL_UNAVAILABLE 로 온다. 대화 띠의 붉은 한 줄이 그것이다.

모든 오류가 같은 모양으로 온다

Error:
  type: object
  required: [code, message]
  properties:
    code:    { $ref: '#/components/schemas/ErrorCode' }
    message: { type: string }            # 화면에 그대로 띄울 수 있는 문장
    hint:    { type: string, nullable: true }
hint 가 있는 이유 — 화면은 “왜 안 되는지”가 아니라 “무엇을 하면 되는지”를 말해야 한다. MUSIC_APP_NOT_RUNNING 의 hint 는 open -a Music 이다.
