# Relay — 서비스 정의

> 산출물 ①. `판교_3반_Relay-개요.pdf`의 1~2장 재료.

---

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | **Relay** |
| 한 줄 정의 | 미팅 전·중·후를 하나로 잇는 어시스턴트. 상대 질문에는 답을 주고, 내가 물어야 할 것은 놓치지 않게 한다 |
| 타겟 사용자 | 고객·지원자를 만나는 사람 — **세일즈, PM, CS, 면접관** |
| 없애려는 것 | **"확인해보고 연락드리겠습니다"** 와 **"그거 물어본다는 걸 깜빡했네"** |

이름의 의미: 팀이 가진 답을 필요한 자리로 **이어준다(relay)**.

---

## 2. 문제 정의

### 현황 — 미팅에서 두 가지가 동시에 실패한다

**① 상대가 묻는데 답을 못 한다**

B2B 미팅에서 고객 질문의 상당수는 제품·개발 영역이다.

- "그 기능 언제 나오나요?"
- "저희가 요청한 버그는 고쳐졌나요?"
- "온프레미스 지원되나요?"

세일즈·PM은 즉답할 수 없다. 그래서 **"확인해보고 연락드리겠습니다"** 가 나온다.

**② 내가 물어야 할 것을 못 묻는다**

미팅에 들어가기 전에는 목표가 있다.

- 예산 규모와 집행 시점
- 의사결정 절차와 결정권자
- 기존 시스템 연동 범위

그런데 대화가 상대 페이스로 흘러가면 **끝나고 나서야 깨닫는다.**
"예산 얘기를 못 했네." 다시 잡는 미팅이 한 번 더 생긴다.

### 원인

**①의 원인 — 답은 있는데 형태가 다르다**

답은 이미 존재한다. GitHub에.

| 고객 질문 | 답이 있는 곳 |
|---|---|
| "그 기능 언제 나오나요" | 이슈, 마일스톤, PR |
| "그 버그 고쳐졌나요" | 머지된 PR, 릴리즈 노트 |
| "이번 버전에 뭐가 바뀌었나요" | 릴리즈 노트, CHANGELOG |

문제는 **형태**다.

| GitHub의 언어 | 고객에게 필요한 언어 |
|---|---|
| `fix(auth): resolve token refresh race condition (#2841)` | "인증 토큰 갱신 이슈가 2월 릴리즈에 반영됐습니다" |
| 열린 이슈, 마일스톤 `v2.4` | (말하면 안 됨 — 확정 아님) |
| 라벨 `wontfix` | "현재 로드맵에는 없습니다" |

**개발자에게 자명한 정보가 세일즈에게는 해독 불가이고, 그중 일부는 애초에
고객에게 말하면 안 되는 미확정 정보다.** 검색으로는 이 둘을 구분할 수 없다.

**②의 원인 — 목표를 기억에 의존한다**

미팅 목표를 노트에 적어도, **대화 중에 그 노트를 볼 여유가 없다.**
상대 발화에 반응하느라 내 아젠다는 뒤로 밀린다.

### 배경 — 기존 도구로 안 되는 이유

| 도구 | 하는 일 | 못 하는 일 |
|---|---|---|
| 사내 위키 | 문서 검색 | 뭘 써야 할지 모름 → 항상 비어 있음 |
| 슬랙 검색 | 과거 대화 검색 | 답이 스레드에 묻힘 |
| GitHub 검색 | 이슈/PR 검색 | 개발자 언어 그대로. **확정/미확정 구분 없음** |
| 기존 RAG 도구 | 문서를 찾아 보여줌 | 못 찾으면 끝. **실패가 기록되지 않음** |
| 회의록 도구 | 사후 요약 | **미팅 중에는 아무것도 안 해줌** |

마지막 두 항목이 핵심이다. **실시간 도구는 사후를 안 보고, 사후 도구는 실시간을 안 본다.**

## 3. 해결 방식 — 미팅을 세 단계로 잇는다

```
Before        참석자와 목표를 정하고, 준비된 답변으로 무장한다
   ↓
In Progress   상대 질문에 즉답하고, 내 목표가 다뤄졌는지 체크한다
   ↓
After         요약·할 일·개선점을 남긴다
   ↓
              (할 일을 처리하면 다음 미팅의 Before가 된다)
```

**After가 다음 Before로 이어지면서 순환이 완성된다.** 직선이 아니라 원이다.

### 핵심 설계 — 대화를 양방향으로 본다

기존 도구는 한 방향만 본다. Relay는 두 방향을 함께 추적한다.

| 방향 | 데이터 | 시스템이 하는 일 |
|---|---|---|
| 상대 → 나 | `question` | 할 말을 제공한다 |
| **나 → 상대** | **`session_goal`** | **물었는지 확인한다** |

이 때문에 지표도 두 개다.

| 지표 | 의미 |
|---|---|
| **즉답률** | 상대 질문에 얼마나 그 자리에서 답했나 |
| **목표 달성률** | 내가 물으려던 걸 얼마나 물었나 |

## 4. 각 단계에서 일어나는 일

### Before — 무장하고 들어간다

```
상대 조직    Acme Corp
상황        NDA 미체결 · discovery 단계
참석자      김OO · 정보보안팀장 · "작년에 보안감사 이슈 겪음"
물어볼 것    1. 예산 규모와 집행 시점
            2. 의사결정 절차
            3. 기존 시스템 연동 범위
```

`상황`이 그냥 메모가 아니라 **검색 필터**가 된다. NDA 미체결이면
대외 비공개 정보는 애초에 검색되지 않는다.

### In Progress — 두 가지가 동시에 돈다

```
고객: 셀프호스팅에서 SAML SSO를 설정할 수 있나요?
      🟢 셀프호스팅에서 SAML SSO 지원              (0.3초)
         "SAML 2.0 기반 SSO를 지원하며…"
         PR #43386 · 2026-09

고객: 저희 올해 예산이 3억 정도인데요.
      ✓ 목표 1 "예산 규모 확인" 체크됨            ← 내가 안 물어도 충족

고객: Edge Functions는 셀프호스팅에서 언제 지원되나요?
      🔴 일정 확인 필요
         "내부 확인 후 내일까지 회신드리겠습니다.
          셀프호스팅에서 특히 필요한 기능이…"      ← 역질문으로 다음 재료 확보
```

**사용자는 아무것도 입력하지 않는다.** 상대가 말을 끝내면 화면이 저절로 바뀐다.

### After — 남기고 넘긴다

```
목표 달성 2/3 (66%)    즉답 3/4 (75%)

요약     금융권 고객으로 데이터 반출 제약이 크다.
        온프레미스와 SSO가 핵심 관심사이며…

개선점   예산은 확인했으나 의사결정 절차를 묻지 못했다.
        다음 미팅에서 먼저 꺼낼 것.

할 일
  □ [답변필요] Edge Functions 셀프호스팅 지원 시점
  □ [할일]     의사결정 절차 확인          ← 못 다룬 목표가 이월됨
  □ [할일]     보안 백서 발송
  □ [개선]     초반에 목표를 먼저 꺼낼 것
```

**`[답변필요]` 항목을 처리하면 다음 미팅에서 🟢가 된다.** 여기가 순환의 연결점이다.

## 5. 핵심 가치 4가지

| # | 가치 | 구현 |
|---|---|---|
| 1 | **번역** | 개발자 언어 → 고객 언어 |
| 2 | **선별** | 확정된 정보만 통과. 미확정은 사람 승인 후에만 |
| 3 | **양방향** | 상대 질문 + 내 목표를 함께 추적 |
| 4 | **순환** | 못 한 답이 다음 미팅의 답이 됨 |

## 6. GitHub을 다루는 방식 — 소스별 신뢰 등급

**모든 GitHub 데이터를 같게 취급하지 않는다.** 인입 시점에 소스 종류로
`audience_level`을 **강제 지정**한다.

| GitHub 소스 | 성격 | `audience_level` | 고객에게 |
|---|---|---|---|
| 릴리즈 / 태그 | **확정 사실** | `public` | 즉답 가능 |
| 머지된 PR | **확정 사실** | `public` | 즉답 가능 |
| CHANGELOG | 확정 사실 | `public` | 즉답 가능 |
| 열린 이슈 | **미확정** | `internal` | **승인 후에만** |
| 마일스톤 / 로드맵 | **미확정 (일정)** | `internal` | **승인 후에만** |

> **이 매핑이 LLM 프롬프트가 아니라 인입 파이프라인의 규칙이라는 게 핵심이다.**
> 모델이 실수해도 `internal` 청크는 `public` 세션의 검색 결과에 애초에 안 나온다.
> 검색 단계 WHERE 절에서 차단된다.

### 결과

- **"버그 고쳐졌나요"** → 머지된 PR = 확정 → 🟢 즉답
- **"기능 언제 나오나요"** → 열린 마일스톤 = 미확정 → 🔴 보류 + 할 일 생성
  → 담당자가 "3월 목표이나 대외 공지 전"이라고 답변 작성 → 다음부터 조건부 답변

**같은 GitHub인데 답의 성격이 갈린다.** 이게 검색 도구와의 결정적 차이다.

## 7. 액터

| Actor | 화면 | 단계 | 하는 일 |
|---|---|---|---|
| **발화자** (세일즈/PM) | 실시간 어시스트 패널 | Before + In Progress | 목표를 정하고, 미팅 중 판정과 문구를 본다 |
| **정리자** (보통 본인) | 회의 결과 | After | 요약을 확인하고 할 일을 처리한다 |
| **지식 관리자** (제품팀) | 준비된 답변 관리 | 상시 | 답변을 작성·수정하고 소스를 관리한다 |

## 8. 성공 지표

```
즉답률        미팅에서 그 자리에 답한 질문의 비율
목표 달성률    물으려던 것 중 실제로 다룬 비율
```

검색 정확도나 응답 속도가 아니라 **미팅이 실제로 잘 굴러갔는가**를 측정한다.

부수 지표
- 답변 필요 할 일이 처리되는 속도
- 준비된 답변의 실제 사용 횟수

## 9. 범위

### 한다
- 화상 + 대면 미팅 (오디오 로컬 캡처, 봇 미참여)
- 화자 구분: **나 vs 나 아님** (참가자 테이블로 1:N 확장 가능)
- 지식 소스: **GitHub** (이슈 / PR / 릴리즈 / 마일스톤)

### 안 한다
| 제외 | 이유 |
|---|---|
| 고객 화면 노출 | 담당자 본인 전용 도구 |
| 자동 발송 | 문구 제안만. 말하는 주체는 사람 |
| CRM 연동 | 세션 컨텍스트는 수동 입력 |
| Slack 연동 | 범위 관리 — 고려사항에 확장 계획으로 기재 |
| 코드 자체 분석 | 메타데이터(이슈/PR/릴리즈)만 사용 |

## 10. 실현 가능성 근거

| 선례 | 검증된 것 |
|---|---|
| **Balto** | 라이브 통화 중 배틀카드 실시간 제시. 누적 **4억 통** |
| **Cresta** | **200ms 이내** next-best-action 제시 |
| **Gong / Chorus** | 미팅 사후 요약·코칭. After 단계의 선례 |
| **Granola / Meetily** | 봇 없이 마이크+시스템 오디오 로컬 캡처 |
| **AssemblyAI 스트리밍 diarization** | 실시간 화자분리 P50 **307ms** (실통화 400만건) |

**실시간 가이던스와 사후 요약은 각각 검증된 카테고리다.**
Relay의 차이는 **둘을 하나로 잇고, 대화를 양방향으로 보며,
미확정 정보를 구조적으로 차단한다는 것.**
