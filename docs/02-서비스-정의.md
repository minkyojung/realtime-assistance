## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | **Relay** |
| 한 줄 정의 | 개발팀의 날것 정보를 **세일즈가 입에 낼 수 있는 문장**으로 바꿔, 미팅 중 실시간으로 건네주는 어시스턴트 |
| 타겟 사용자 | 개발 조직 밖에서 고객을 만나는 사람 — **세일즈, PM, CS** |
| 없애려는 말 | **"확인해보고 연락드리겠습니다"** |

이름의 의미: 개발팀 → 세일즈로 답을 **이어준다(relay)**.

## 2. 문제 정의

### 현황

B2B 미팅에서 고객 질문의 상당수는 **제품·개발 영역**이다.

- "그 기능 언제 나오나요?"
- "저희 요청한 버그는 고쳐졌나요?"
- "온프레미스 지원되나요?"

세일즈·PM은 이 질문에 **즉답할 수 없다.** 그래서 나오는 말이
"확인해보고 연락드리겠습니다"이고, 그 뒤에 이런 일이 벌어진다.

```
미팅 중 질문 발생
  → 누구에게 물어야 하는지 모름
  → 슬랙에 질문 (하루 대기)
  → 개발자가 GitHub 이슈 링크를 던져줌
  → 세일즈가 그 내용을 해석 못 함
  → 다시 질문 (또 하루)
  → 2~3일 뒤 고객에게 회신
```

### 원인 — 문제는 정보가 없는 게 아니다

**답은 이미 존재한다. GitHub에.**

| 고객 질문 | 답이 있는 곳 |
|---|---|
| "그 기능 언제 나오나요" | 이슈, 마일스톤, PR |
| "그 버그 고쳐졌나요" | 머지된 PR, 릴리즈 노트 |
| "이번 버전에 뭐가 바뀌었나요" | 릴리즈 노트, CHANGELOG |

문제는 **형태**다.

| GitHub의 언어 | 고객에게 필요한 언어 |
|---|---|
| `fix(auth): resolve token refresh race condition (#2841)` | "인증 토큰 갱신 관련 이슈가 2월 릴리즈에 반영됐습니다" |
| 열린 이슈, 마일스톤 `v2.4` | (말하면 안 됨 — 확정 아님) |
| 라벨 `wontfix` | "현재 로드맵에는 없습니다" |

**개발자에게 자명한 정보가 세일즈에게는 해독 불가이고, 그중 일부는 애초에
고객에게 말하면 안 되는 미확정 정보다.** 검색으로는 이 둘을 구분할 수 없다.

### 배경 — 왜 기존 도구로 안 되는가

| 도구 | 하는 일 | 못 하는 일 |
|---|---|---|
| 사내 위키 | 문서 검색 | **뭘 써야 할지 아무도 모름** → 항상 비어 있음 |
| 슬랙 검색 | 과거 대화 검색 | 답이 스레드에 묻힘, 신뢰도 불명 |
| GitHub 검색 | 이슈/PR 검색 | 개발자 언어 그대로. **확정/미확정 구분 없음** |
| 기존 RAG 도구 | 문서를 찾아 보여줌 | **못 찾으면 거기서 끝. 실패가 기록되지 않음** |

마지막 항목이 핵심이다. **기존 도구는 실패해도 아무것도 남기지 않는다.**

## 3. 해결 방식

### 핵심 주장

> **"확인해보고 연락드리겠습니다"가 나올 때마다 시스템이 기록하고,
> 답을 채우고, 다음번엔 그 말이 안 나오게 만든다."**

### 3막 루프

```
1막  미팅 중   질문 감지 → 답 없음
                🟡 지금 할 말 제공 + knowledge_gap 생성 (담당자에게 전달)

2막  사후      개발팀이 큐에서 공백을 확인
                GitHub 원문 → 고객용 문장으로 확정 → response_rule 생성

3막  다음 미팅  같은 질문 → 🟢 1.5초 즉답
```

`response_rule.created_from ↔ knowledge_gap.resolved_by` 양방향 FK가
**"쓸수록 좋아진다"의 데이터 증거.**

### 핵심 가치 3가지

| # | 가치 | 구현 |
|---|---|---|
| 1 | **번역** | 개발자 언어 → 고객 언어 |
| 2 | **선별** | 확정된 정보만 통과. 미확정은 사람 승인 후에만 |
| 3 | **축적** | 답 못 한 질문이 다음 답이 됨 |

## 4. GitHub을 다루는 방식 — 소스별 신뢰 등급

**모든 GitHub 데이터를 같게 취급하지 않는다.** 인입 시점에
소스 종류로 `audience_level`을 **강제 지정**한다.

| GitHub 소스 | 성격 | `audience_level` | 고객에게 |
|---|---|---|---|
| 릴리즈 노트 / 태그 | **확정 사실** | `public` | 즉답 가능 |
| 머지된 PR | **확정 사실** | `public` | 즉답 가능 |
| CHANGELOG | 확정 사실 | `public` | 즉답 가능 |
| 열린 이슈 | **미확정** | `internal` | **승인 후에만** |
| 마일스톤 / 로드맵 | **미확정 (일정)** | `internal` | **승인 후에만** |
| 내부 논의 코멘트 | 미확정 | `internal` | 승인 후에만 |

> **이 매핑이 LLM 프롬프트가 아니라 인입 파이프라인의 규칙이라는 게 중요하다.**
> 모델이 실수해도 `internal` 청크는 `public` 세션의 검색 결과에 애초에 안 나온다.
> (검색 단계 WHERE 절에서 차단 — 원칙 2)

### 결과

- **"버그 고쳐졌나요"** → 머지된 PR = 확정 → 🟢 즉답
- **"기능 언제 나오나요"** → 열린 마일스톤 = 미확정 → 🟡 보류 + 공백 생성
  → PM이 "3월 목표이나 대외 공지 전" 이라고 승인 → 다음부터 조건부 답변

**같은 GitHub인데 답의 성격이 갈린다.** 이게 검색 도구와의 결정적 차이.

## 5. 액터

| Actor | 화면 | 하는 일 |
|---|---|---|
| **발화자** (세일즈/PM) | 실시간 어시스트 패널 | 미팅 중 판정과 문구를 본다. 아무것도 입력하지 않는다 |
| **정보 승인자** (개발팀/PM) | 지식 공백 큐 | 답 못 한 질문을 고객용 문장으로 확정한다 |
| **지식 관리자** | 답변 규칙 관리 | 소스 연결, `audience_level` 관리, 만료 규칙 갱신 |

## 6. 성공 지표

```
1주차 : 질문 100건 중 60건이 "확인 후 회신"   (커버리지 40%)
4주차 : 질문 100건 중 15건이 "확인 후 회신"   (커버리지 85%)
```

검색 정확도나 응답 속도가 아니라 **"모름"이 줄어드는 속도**가 지표다.

부수 지표
- T0(즉답 캐시) 히트율 상승 → P50 응답 지연 하락
- 공백 → 규칙 전환율, 공백 평균 해소 시간

## 7. 범위

### 한다
- 화상 + 대면 미팅 (오디오 로컬 캡처, 봇 미참여)
- 화자 구분: **나 vs 나 아님** (참가자 테이블로 1:N 확장 가능)
- 지식 소스: **GitHub** (이슈 / PR / 릴리즈 / 마일스톤)

### 안 한다
| 제외 | 이유 |
|---|---|
| 고객 화면 노출 | 담당자 본인 전용 도구 |
| 자동 발송 | 문구 제안만. 말하는 주체는 사람 |
| CRM 연동 | 세션 컨텍스트는 수동 입력 |
| Slack 연동 | 범위 관리 — 고려사항에 확장 계획으로 기재 |
| 코드 자체 분석 | 메타데이터(이슈/PR/릴리즈)만 사용 |

## 8. 실현 가능성 근거

| 선례 | 검증된 것 |
|---|---|
| **Balto** | 라이브 통화 중 배틀카드 실시간 제시. 누적 **4억 통** |
| **Cresta** | **200ms 이내** next-best-action 제시 |
| **Granola / Meetily** | 봇 없이 마이크+시스템 오디오 로컬 캡처 |
| **AssemblyAI 스트리밍 diarization** | 실시간 화자분리 P50 **307ms** (실통화 400만건 벤치) |

**실시간 가이던스는 이미 검증된 카테고리다.**
Relay의 차이는 **지식 소스를 GitHub으로 잡고, 미확정 정보를 구조적으로 차단하며,
못 한 답이 다음 답이 되는 루프를 가진 것.**
