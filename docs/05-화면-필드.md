# 화면 1. 실시간 어시스트 패널

담당 액터: 발화자 (A1~A13) · 데스크톱 앱 (440×900)

## 레이아웃 원칙 3가지

### ① 유리는 한 겹만

Apple HIG는 **뷰당 primary glass sheet 하나**를 권하고 **glass on glass를 금지**한다.
과용하면 무엇이 눌리는 것인지 구분이 안 되고 시각적 소음이 된다.

| 요소 | 재질 |
|---|---|
| **상단 pill** | **Liquid Glass** |
| 대화 버블 | 불투명 |
| **하단 제안** | **불투명** — 실제로 읽어야 하는 문장. 블러 위 텍스트는 4.5:1 대비를 못 맞춘다 |

### ② 제안은 대화가 아니라 시스템 출력이다

제안을 대화 흐름에 섞으면 **"이것도 누가 말한 것"처럼 읽힌다.**
실제로는 아무도 말하지 않은, 아직 존재하지 않는 문장이다.

Apple이 "시스템이 먼저 제안하는 것"을 다루는 방식은 전부 **콘텐츠와 다른 층**이다.
QuickType은 입력창 위 고정, Live Activity는 콘텐츠 위 레이어, Inspector는 옆.
**콘텐츠 흐름 안에 섞는 사례가 없다.**

→ 제안은 **하단 고정**. QuickType과 같은 자리다.

### ③ 앵커가 없으므로 위치의 안정성이 전부다

보통 UI는 사용자가 누를 것을 전제한다. 그런데 제안은 다르다.

```
사용자가 하는 일:  읽는다 → 입으로 말한다
클릭 없음. 복사 없음. 전송 없음.
```

**액션 지점이 화면 밖(사용자의 입)에 있다.** 붙일 앵커가 없으므로
원칙은 하나만 남는다 — 가장 안정적으로 눈이 가는 자리.

### pill에서 뺀 것과 이유

| 뺀 것 | 이유 |
|---|---|
| 앱 이름 `Relay` | 창이 곧 앱이다 |
| 도메인 배지 `sales` | 세션 내내 안 바뀌고 이미 알고 있다 |
| 답변 카운트 | 정보 3개 상한을 넘긴다 |

**`NDA 미체결`을 탭하면 즉시 토글된다.** 이 값이 검색 필터를 바꾸므로
미팅 중 상태 변경이 한 번의 동작이어야 한다.

## ④ 제안 (하단 고정)

**항상 최신 것 하나만.** 새 질문이 오면 교체되고, 이전 것은 ③ 흐름 안에 접힌 한 줄로 남는다.

| 화면 요소 | 필드 | 타입 | 출처 | 시점 |
|---|---|---|---|---|
| **질문 인용** | `normalized_text` | text | `question.normalized_text` | 푸시 |
| 판정 색·라벨 | `response_mode` | enum | `question.response_mode` | 푸시 |
| **한 줄 요약** | `headline` | text | **생성 없음 — 템플릿** | 푸시 |
| 의도 배지 | `intent` | enum | `question.intent` | 푸시 |
| **할 말 문구** | `suggested_script` | text | `response_rule.suggested_script` **(조인)** | 스트리밍 |
| 조건 경고 | `condition` | text | `response_rule.condition` **(조인)** | 푸시 |
| 출처 | `source_type`, `external_ref`, `valid_from`, `source_url` | — | `knowledge_chunk` | 푸시 |
| 근거 건수 | `evidence_count` | int | 계산 | 푸시 |
| 응답 지연 | `latency_ms` | int | `question.latency_ms` | 푸시 |

### 질문 인용이 필요한 이유

질문 두 개가 빠르게 연달아 오면 하단 제안이 **어느 질문 것인지 헷갈린다.**
Mail의 답장 인용, Slack의 스레드 미리보기와 같은 방식으로 한 줄 붙인다.

### 근거는 펼치지 않는다

미팅 중 필요한 것은 근거를 **읽는** 것이 아니라 **확인**하는 것이다.
펼침(Collapsible)은 스크롤을 밀어 대화 흐름을 놓치게 한다.

```
PR #43386 · 2026-09 · 외 2건 ↗     ← 항상 노출. 클릭 시 GitHub 원문
```

`PR`/`릴리즈`/`이슈` 라벨과 시점만으로 신뢰 판단의 대부분이 끝난다.

### 높이 규칙 — 바뀌지만 예측 가능하게

| 상황 | 하단 영역 |
|---|---|
| 질문 없음 | **얇은 바** — `듣는 중` |
| 질문 감지 | 펼쳐짐 + **3줄 자리 예약** (스켈레톤) |
| 판정 도착 (~0.3초) | 색·요약 즉시 표시 |
| 문구 도착 (~1.5초) | 예약된 자리에 스트리밍 |
| 새 질문 | 교체. 이전 건 ③에 접혀서 남음 |

**높이가 먼저 확정되고 글자가 그 안을 채운다.** 대화 영역이 밀리지 않는다.

## 두 종류의 스트리밍

| | 언제 | 이벤트 |
|---|---|---|
| ① 발화 자막 | 말하는 동안 | `utterance.partial` |
| ② 제안 문구 | 말이 끝난 뒤 | `question.delta` |

판정(색 + 요약)은 ②보다 먼저 도착한다. **0.3초에 상황을 파악**하고 문구는 읽기 시작할 때쯤 채워진다.

사용자 입장에서 **"회의 끝나고 처리할 것"** 이라는 점이 같다. 구분해야 할 이유가 없다.

저장하면 `response_rule`이 생겨 **다음 미팅에서 🟢로 나온다.**

### 인입 규칙 (상수, 화면에 표시)

| GitHub 소스 | `audience_level` |
|---|---|
| 릴리즈 / 태그 / CHANGELOG | `public` |
| 머지된 PR | `public` |
| 열린 이슈 | `internal` |
| 마일스톤 / 로드맵 | `internal` |

**이 매핑이 LLM 프롬프트가 아니라 인입 파이프라인의 규칙이라는 점이 핵심이다.**
모델이 실수해도 `internal` 청크는 `public` 세션의 검색 결과에 들어올 수 없다.

# 정합성 규칙 (ERD·API 작업 시 준수)

1. 이 문서에 없는 필드는 ERD·API에 넣지 않는다
2. 이 문서에 있는 필드는 ERD·API에 반드시 넣는다
3. `시점` 열이 `요청`이면 대응 API 엔드포인트가 존재해야 한다
4. `출처`가 `계산`이면 ERD 컬럼이 아니라 API 응답 필드다
5. 예외 상태의 오류 코드(400/401/404/409)는 API 명세에 정의한다
