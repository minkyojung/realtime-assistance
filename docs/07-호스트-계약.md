# 호스트 계약

> 터미널 안에 여러 앱을 담는 껍데기가 무엇을 갖고, 앱에게 무엇을 요구하는가.
> 작성일: 2026-09-09

---

## 0. 한 줄

```
호스트가 파는 것은 화면이 아니라 조작법이다. 화면은 앱이 그린다.
```

---

## 1. 호스트가 가진 것 — 두 줄

```
┌──────────────────────────────────────────────┐
│                                              │
│          앱 본문 — 앱이 전부 그린다            │
│                                              │
├──────────────────────────────────────────────┤
│ › 입력창                                      │  ← 호스트
├──────────────────────────────────────────────┤
│ Recently Added · 157   ▶ Perth · Slack 3  $0.02│  ← 호스트
└──────────────────────────────────────────────┘
```

**입력창 한 줄, 상태줄 한 줄.** 그 위는 앱의 것이다.

그래서 앱마다 화면이 달라도 된다. 음악은 목록을 그리고, 채팅은 대화를 그린다.
음악에 채널 목록을 붙일 이유도, 채팅에 재생 바를 붙일 이유도 없다.

**상태줄은 모든 앱의 상태를 모은다.** 채팅을 보는 중에도 무엇이 재생 중인지
보이고, 음악을 보는 중에도 안 읽은 메시지 수가 보인다. 맥의 메뉴바와 같다.

---

## 2. 조작법 — 이것이 호스트의 유일한 자산

| | 뜻 |
|---|---|
| **입력창** | 모든 것의 입구. 앱이 바뀌어도 여기는 안 바뀐다 |
| **글자** | 의도 — "조용한 거", "누가 나 찾았어?" |
| **`/`** | **갈 곳과 할 것.** 사이드바를 대신한다 |
| **`ctrl+f`** | 지금 보고 있는 것 안에서 찾기 |
| **`ctrl+j`** | 로그 펼치기 |
| **`tab`** | 앱 안에서 다음 |
| **`ctrl+tab`** | 다음 앱 |
| **`?`** | 도움말 |
| **`esc`** | 한 단계 물러나기 |
| **`ctrl+c`** | 종료 |

### 칸 배분은 호스트가 준다

터미널은 폭이 예측 불가하고 폰트 메트릭이 없다. 그래서 **"자를지 말지"를
앱이 정해야 하고, 자르는 것은 곧 우선순위 선언이다.**

모든 TUI 레이아웃은 칸마다 숫자 넷을 정하는 일로 환원된다.

| | 뜻 |
|---|---|
| `Min` | 이보다 좁아지면 이 칸은 사라진다 |
| `Weight` | 남는 공간을 가져가는 비율 |
| `Max` | 더 넓어지지 않는다. 없으면 한 칸이 다 먹고 가운데가 빈다 |
| `Drop` | 좁아질 때 희생되는 순서. 0 이면 절대 안 버린다 |

`style.Columns` 가 이 선언을 실행한다. 음악만의 문제가 아니다 —
채팅 앱도 좁아지면 시각과 채널명 중 무엇을 버릴지 정해야 한다.

```
음악 목록                       좁아지는 순서
제목      Min 14 Max 58 Drop 0   ← 절대 안 버린다
아티스트   Min 10 Max 26 Drop 2
재생수    Min  3        Drop 3   ← 제일 먼저 버린다
길이      Min  4        Drop 1
```

### 관통하는 원칙

```
화면에 상시로 자리를 주지 않는다. 필요할 때 입력창에서 불러낸다.
```

이 한 줄에서 아래가 전부 따라 나온다.

| 결정 | 근거 |
|---|---|
| 사이드바를 없앤다 | "갈 수 있는 곳"은 상시로 볼 필요가 없다. `/` 가 보여준다 |
| 검색 화면이 없다 | `ctrl+f` 로 지금 목록을 거른다 |
| 명령 팔레트가 입력창 **아래**에 뜬다 | 본문을 밀어내지 않는다. 고르는 동안 보던 것이 그대로 있다 |
| 도움말도 같은 자리 | 같은 이유 |

**사이드바는 상시 17칸(80칸 창의 21%)을 먹는다.** 그 대가로 얻는 것이
"목록을 항상 본다"인데, 터미널에서는 가로가 세로보다 귀하다.

### 팔레트는 본문을 밀어내지 않는다

처음에는 본문 자리를 통째로 빌려 썼다. 그런데 명령을 고르는 동안 보고
있던 목록이 사라져 **맥락을 잃고**, 눈도 화면 위아래를 왕복해야 했다.

입력창 바로 아래에 붙이면 둘 다 사라진다. agentic CLI 의 관례이기도 하다.

```
 ▌ Please Wait for Me          Busker Busker   177  1:21   ← 본문 그대로
   Peanut butter Sandwich       jisokuryClub    36  3:51
 ─────────────────────────────────────────────────────────
 › /
 ▌ /queue                        jump to the current queue  ← 여기
   /unplayed             tracks you added but never played
 ─────────────────────────────────────────────────────────
 Recently Added · 157
```

목록 높이 상한(14줄) 덕분에 **보통 크기의 터미널에서는 본문이 한 줄도
안 밀린다.**

## 2-B. 로그 — 호스트의 세 번째 자산

입력의 짝이다. **입력이 전역이면 출력도 전역이어야 한다.**

한 문장이 여러 앱에 갈 수 있으므로("조용한 거 틀고 슬랙도 꺼줘")
대화는 **어느 앱에도 속하지 않는다.** 앱을 바꿔도 이어져야 하고,
여러 앱에 걸친 요청의 결과가 착지할 곳도 여기뿐이다.

```
문장을 만드는 것은 앱,  보관하고 보여주는 것은 호스트
      ↕                        ↕
프로세스가 stdout 에 쓰고,  터미널이 스크롤백을 갖는다
```

| | |
|---|---|
| `›` | 사용자가 한 말 |
| `▸ 앱이름` | 앱이 한 말. **앱이 하나뿐이면 이름 생략** |
| `▸` (앰버) | 실패. 실패도 대화의 일부다 |
| 자리 | **입력창 바로 위.** 팔레트는 바로 아래 |
| 평소 | 마지막 한 줄만. 기다리는 중이면 방금 한 말 + 스피너 |
| `ctrl+j` | 펼침 (최대 8줄) |
| 보관 | 세션 동안만. 저장하지 않는다 |

### 곡별 근거와 큐 설명은 다른 물건이다

| | 어디 | 누구 것 |
|---|---|---|
| 곡마다 붙는 근거 | 목록·본문 | **앱** — 곡의 속성이다 |
| 큐 전체 한 문장 | 로그 | **호스트** — 대화의 일부다 |

*"40일 전에 담고 한 번도 안 들었습니다"* 는 곡에 붙고,
*"8곡 31분짜리로 짰어요"* 는 대화로 간다.

## 3. 앱의 의무

### 3-1. 앱은 자기 키 바인딩을 만들지 않는다

하고 싶은 것이 있으면 `Commands()` 로 등록한다.

앱이 각자 단축키를 만들면 조작법이 앱마다 달라지고, 그러면 이것은
그냥 tmux 가 된다. **처음 여는 앱에서도 `/` 를 누르면 뭘 할 수 있는지 보이고,
`⌕` 로 찾고, `tab` 으로 넘길 수 있어야 한다.**

### 3-2. 앱은 자기 크기를 기억하지 않는다

`View(width, height)` 로 그릴 때마다 받는다.
`WindowSizeMsg` 를 자식에게 전달하고 각자 기억하게 하면 상태가 늘고 어긋난다.

### 3-3. 앱은 배경에서도 상태를 보고한다

`Status()` 와 `Badge()` 는 포커스가 없어도 호출된다.

## 4. 인터페이스

`internal/app/app.go` 참조. 각 항목의 근거는 실측이나 조사에서 나왔다.

| 항목 | 왜 이 모양인가 |
|---|---|
| `Update` 가 `App` 을 반환 | `tea.Model` 을 반환하면 호스트가 메시지마다 타입 단언을 해야 한다. Bubble Tea 에서 반복 지적되는 함정 |
| `View(w, h)` | 위 3-2 |
| `Init(send func(tea.Msg))` | Music.app 은 폴링이지만 채팅은 **저쪽에서 밀어 넣는다**(Socket Mode). 이벤트 루프 밖에서 메시지를 넣을 통로가 없으면 그런 앱을 담을 수 없다 |
| `Ready() error` | 앱마다 관문이 다르다. 음악은 macOS 자동화 권한, 채팅은 로그인 |
| `Description()` | 라우터가 "이 문장이 어느 앱 것인지" 판단하는 유일한 근거 |
| `Filter(query) App` | 검색은 즉시 반영되어야 하므로 `Cmd` 를 돌려주지 않는다 |

## 5. 라우팅 — 작은 라우터를 항상 먼저 부른다

한 문장을 받아 어느 앱이 답할지 정하는 것이 호스트의 본체다.

```
입력:      "조용한 거 틀고 슬랙 꺼줘"
컨텍스트:  앱 이름 + Description() (전부 합쳐 200토큰 남짓)
출력:      ["music", "slack"]
```

**처음에는 "앱이 거절하면 그때 옮긴다"로 하려 했으나 두 가지 이유로 버렸다.**

1. 비싸다 — 음악 앱이 7초·$0.01 을 쓰고 "내 거 아님"이라고 하면 그 값을 버린다
2. **표현을 못 한다** — `handled` 는 불리언이라 "두 앱 다"를 말할 수 없다

라우터는 0.3초·$0.0002 다. 7초에 얹으면 체감이 없고, **여러 앱을 지목할 수 있다.**
지금 보고 있는 앱을 힌트로 주면 정확도도 올라간다.

## 6. 만들지 않는 것

[Zellij](https://zellij.dev/documentation/plugins.html) 가 정확히 "터미널
워크스페이스 + 플러그인"을 한다. 그런데 **WASM 플러그인 + Protocol Buffers +
샌드박스**다. 그것이 이 길의 끝이고, 우리는 거기 가지 않는다.

| 안 만드는 것 | 왜 |
|---|---|
| 화면 분할 | tmux 가 이미 한다. 한 번에 한 앱 |
| 플러그인 시스템 | **앱은 컴파일 타임 등록.** 확장성을 여는 순간 Zellij 의 무게가 따라온다 |
| 프로세스 분리 · IPC | 같은 프로세스 함수 호출로 충분하다 |
| 알림 인터럽트 | 지금은 `Badge()` 숫자만. "어디까지 방해해도 되는가"는 답이 정해지지 않은 문제라 미뤄둔다 |

## 7. 앱 목록

| 앱 | 바깥과 통신 | 관문 | 상태 |
|---|---|---|---|
| **music** | AppleScript (Music.app) | macOS 자동화 권한 | 구현됨 |
| chat | HTTPS + WebSocket (Socket Mode) | 앱 등록 + 토큰 2개 | 미착수 |

**통신 방식은 앱마다 다르고, 그 차이는 앱이 자기 안에서 감춘다.**
호스트는 앱이 AppleScript 를 쓰는지 HTTPS 를 쓰는지 모른다.
