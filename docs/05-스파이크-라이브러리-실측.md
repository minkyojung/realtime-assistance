## 2. 서비스 정의에 미치는 영향 ⚠️

### 문제 ① — "3년 이상 무재생" 서사가 성립하지 않는다

라이브러리 자체가 최근에 만들어졌다(`date added` 2026-07-30). **가장 오래된 마지막
재생이 135일 전**이므로 "3년째 안 들은 곡"이 존재하지 않는다.

**조정:** 묘비의 기준을 절대 기간(3년)이 아니라 **상대 기준**으로 바꾼다.

| 기존 | 조정 |
|---|---|
| 3년 이상 무재생 | **한 번도 재생되지 않음** (57곡, 36.3%) + **추가일 대비 미재생 기간 상위 N%** |

`/graveyard` 의 기본 인자를 `3년`이 아니라 `never`(한 번도 안 들은 곡)로 둔다.
라이브러리 나이와 무관하게 항상 동작하고, 실측상 **36.3%**라는 충분히 강한 수치가 나온다.

> **바뀐 한 줄:** "3,000곡 중 94%가 죽어 있다" → **"담아둔 곡의 3분의 1은 한 번도 듣지 않았다"**

### 문제 ② — 규모가 작다

157곡은 L1 무드 태깅 비용이 사실상 0이고 전곡 조회가 2초 미만이다.
**성능 우려는 기우였다.** 다만 기획서의 타겟 사용자 규모(수천 곡) 서술은
"수십~수천 곡"으로 완화한다.

## 3-2. 추가 실측 — 재생 쏠림과 수명 (2026-09-09)

문제 정의를 다시 쓰면서 같은 데이터를 다른 각도로 집계했다.

```
157곡 · 총 재생 777회 · 평균 4.9회

[쏠림]  상위  1곡 = 22.8%   (Please Wait for Me, 177회)
        상위  5곡 = 48.8%
        상위 24곡 = 80.0%   ← 곡의 15%
        0회 56곡 + 1회뿐 42곡 = 98곡 (62.4%)

[수명]  담은 날 → 마지막 재생일 중앙값   19일
        담은 지 하루 만에 끝난 곡        32곡 (32%)
        담은 기간                        10개월 (4월22 5월26 6월58 7월15 8월30)

[맥락]  06-08시 24 · 12-14시 15 · 15-17시 38 · 18-20시 17 · 21-05시 2

[아티스트]  Busker Busker  1곡 담고 177회 (22.8%)
            The 1975      30곡 담고  60회 (곡당 2.0)
            Bon Iver      15곡 담고   1곡만 재생

[스킵]  53곡 94회. 상위 5곡 중 4곡이 라이브 앨범
```

**왜 "미재생 비율"에서 "쏠림·수명"으로 바꿨나.**
미재생 비율(36.3%)은 라이브러리가 오래돼야 설득력이 생긴다. 이 라이브러리는
2개월 된 157곡이라 약하다. 반면 **쏠림과 수명은 라이브러리 나이와 무관하게
성립하고**, 사람이 손으로 고르든 에이전트가 명령형 도구를 부르든 똑같이 나타난다.
그래서 새 문제 정의(`docs/01`)의 근거로 이쪽을 쓴다.

## 3-3. 플레이리스트는 라이브러리의 부분집합이 아니다 (2026-09-09)

TUI 에서 플레이리스트를 열었더니 곡이 대부분 비어 있었다. 원인을 찾아보니
**Apple Music 에서 플레이리스트에만 담고 "라이브러리에 추가"는 하지 않은 곡**이
실제로 다수였다.

| 플레이리스트 | 담긴 곡 | 그중 라이브러리에 있는 곡 |
|---|---|---|
| Favourite Songs | 20 | 20 |
| **CH** | **30** | **2** |
| Ethos | 1 | 1 |
| **from Steve Jobs** | **10** | **0** |

```
라이브러리(library playlist)   157곡
플레이리스트 전용               38곡
────────────────────────────────────
실제로 다뤄야 할 곡            195곡
```

**설계 반영**

- `track.in_library` (dbml) / `Track.inLibrary` (OAS) 를 추가했다
- `Songs · Artists · Albums` 는 `in_library = true` 만 보여준다
- **플레이리스트와 검색은 전부 보여준다** — 담아둔 곳이 어디든 사용자의 음악이다

> 실제 데이터를 넣어 돌려보지 않았으면 발견할 수 없었다.
> `library playlist` 가 곧 전체라고 가정한 것이 틀렸다.

## 4. 확정된 설계 판단

1. **`loved`와 `bpm`은 스키마에서 제외한다** — 전자는 접근 불가, 후자는 값이 없음
2. **`last_played_at`은 NULL 허용이며, NULL이 곧 "한 번도 안 들은 곡"이다** — 묘비의 1차 기준
3. **`persistent_id`가 동기화 키다** — Music.app 재시작에도 유지되는 유일한 식별자
4. **`source`(shared/file)를 저장한다** — 필드 접근 가능 여부가 여기서 갈린다
5. **동기화는 여전히 비동기 잡으로 둔다** — 지금은 2초지만 라이브러리 규모에 비례하고,
   E3(동기화 중) 화면이 이미 설계에 있다
