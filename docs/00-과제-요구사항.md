## 2. 프로젝트 정의서 목차 (PDF 구성)

PDF는 아래 6개 섹션을 순서대로 담습니다.

| # | 섹션 | 내용 |
|---|---|---|
| 1 | 서비스 개요 | 서비스 이름, 서비스 목적(배경), 핵심 가치 및 주요 기능 (사용자 문제 해결) |
| 2 | 시스템 액터 정의 | 액터 식별 (일반 사용자, 관리자, 외부 시스템 등) 및 액터별 제공 기능 |
| 3 | UI 흐름 (와이어프레임) | UI 흐름(로그인, 메인화면, 상세화면 등)과 화면 동작 방식 상세 설명 |
| 4 | 데이터 모델 설계 | 개체(Entity) 정의, 개체 속성(Schema) 및 개체 간 관계 (ERD) |
| 5 | API 명세 정의 | OAS 기반 API 명세 (입력 및 출력) |
| 6 | 고려사항 | 설계 상의 고민, 다음 단계 개발 시 고려 사항 |

## 4. 세부 평가 기준 (체크리스트)

### 4-1. 서비스 정의 — "무엇을 왜 만드는가" + 전체 기준 역할

**반드시 포함할 것**
- [ ] 명확한 서비스 목적 & 타겟 사용자 정의
- [ ] 구체적인 문제 정의 — **원인 / 배경 / 현황** 포함
- [ ] 문제를 해결하는 논리적이고 타당한 기능 제안
- [ ] 서비스 개요 ↔ 기능 요구사항 간 일관성
- [ ] 액터별 기능 정의와 화면 연결

**감점 사유**
- 기능이 문제 해결과 연결되지 않음
- 🔴 **과도하게 큰 범위 (비현실적 서비스)**

---

### 4-2. UI 흐름 및 화면 설계 — "서비스를 어떻게 사용하게 할 것인가"

**반드시 포함할 것**
- [ ] 서비스 요구사항의 **모든** 기능이 UI 흐름에 반영
- [ ] 주요 화면 목록 및 사용자 흐름 흐름도
- [ ] 화면 구성 요소 구체화 (버튼, 입력, 데이터)
- [ ] **예외/오류 시나리오 포함 (가정)**
- [ ] UI ↔ API 데이터 필드 일치

**감점 사유**
- 핵심 기능이 UI에 없음
- 🔴 **UI 데이터와 API 불일치**

---

### 4-3. 데이터 모델 (ERD) — "서비스와 UI를 가능하게 하는 데이터 구조"

**반드시 포함할 것**
- [ ] 서비스 기능을 지원하는 모든 엔티티 정의
- [ ] UI에서 사용하는 모든 데이터 필드 포함
- [ ] **PK/FK 명시 및 관계 정의 (1:N, M:N)**
- [ ] 속성 데이터 타입 및 제약조건 명시
- [ ] API 구조와 일관성 유지

**감점 사유**
- 🔴 **UI 데이터가 ERD에 없음**
- API와 데이터 모델 불일치

---

### 4-4. API 명세 — "서비스·UI·데이터를 연결하는 인터페이스"

**반드시 포함할 것**
- [ ] 모든 서비스 기능을 수행 가능한 API 정의
- [ ] UI 화면별 필요 API 제공
- [ ] Request/Response가 ERD와 일치
- [ ] 적절한 HTTP Method
- [ ] Path / Query / Body 명확히 정의
- [ ] **에러 코드 정의 (400, 401, 404 등)**
- [ ] **공통 스키마 재사용 (`$ref`)**
- [ ] **Security Schemes 제외** (명시적 제외 항목)

**감점 사유**
- 🔵 **UI에서 필요한 API 누락**
- 🔵 **API와 데이터 모델 불일치**

## 5. 실제 채점축 — "3자 정합성"

세부 평가 기준의 감점 사유를 모아보면 결국 하나의 이야기입니다.

```
문제 정의 → 기능 → 화면(UI) → API → ERD
             이 사슬이 한 군데도 끊기면 안 된다
```

| 감점 사유 | 끊어진 지점 |
|---|---|
| 기능이 문제 해결과 연결되지 않음 | 문제 → 기능 |
| 핵심 기능이 UI에 없음 | 기능 → 화면 |
| UI에서 필요한 API 누락 | 화면 → API |
| UI 데이터와 API 불일치 | 화면 ↔ API |
| UI 데이터가 ERD에 없음 | 화면 → ERD |
| API와 데이터 모델 불일치 | API ↔ ERD |

**→ 대응: 추적 매트릭스 1장을 만든다.**
와이어프레임의 모든 필드에 대해 `화면 · 필드 → API 엔드포인트 · 응답 필드 → 테이블 · 컬럼`을 표로 매핑하고, 발표 슬라이드에 넣습니다. 40점 구간을 방어하는 가장 효율적인 산출물입니다.

---

## 6. 창의성은 채점하지 않는다

> 목표 시스템 정의(30점) 항목: **`구현 및 기능 명확성(O), 창의/특장성(X)`**

- 아이디어의 참신함은 점수원이 **아닙니다**.
- "판정형" vs "어시스턴트형" 같은 컨셉 선택은 점수에 직접 영향이 없습니다.
- 대신 **정의가 명확한가 / 문서 3종이 서로 어긋나지 않는가**가 전부입니다.
- 컨셉은 "설명하기 쉬운 쪽"으로 고르는 것이 발표(10점)에도 유리합니다.

## 9. 작업 순서 원칙

```
① 서비스 정의 → ② 화면(UI) → ③ ERD → ④ API → ⑤ PDF 조립 → ⑥ (여유 시) MVP
```

**화면을 먼저 그려야 필요한 데이터가 도출되고, 그래야 ERD와 API가 UI와 어긋나지 않습니다.**
반대 순서로 진행하면 "UI 데이터가 ERD에 없음" 감점이 사실상 확정됩니다.
